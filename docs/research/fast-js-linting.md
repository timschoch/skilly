# Oxc overtakes ESLint at every gate

Researched 2026-10-21. Decision: [ADR-0006](../adr/0006-oxlint-and-an-edit-hook.md).

As of October 2026, the Oxc stack is the best default for every step of an agent-heavy flow. That stack is **Oxlint 1.89 for linting, tsgolint v7 for type-aware rules (stable since 22 July 2026) and oxfmt for formatting**. Biome 2.6 remains the stronger pick only when a repo wants one mature binary that also formats CSS, YAML and Markdown and can live without deep type-aware rules. ESLint stalled on speed. Its only lever is `--concurrency`, worth about 1.3x in typical repos. typescript-eslint cannot run on TypeScript 7 until the 7.1 API ships, and Oxlint plus tsgolint sidesteps that because it binds to TypeScript 7 directly. TypeScript 7 (GA 8 July 2026) makes `tsc` roughly 9-12x faster on large repos. Combined with `oxlint --type-check`, a single CI pass can report both lint and compiler errors. On Matt Pocock: the research found **no Pocock short, video or post naming Oxlint, Biome, oxfmt, tsgo or Vite+**. His published stance is typecheck plus tests plus Husky and lint-staged running Prettier, with ESLint optional. Treat the "recent statement" as unverified until someone supplies a link. For skilly the recommendation is one per-step stack: oxlint and oxfmt on the edited file in the hook, the same on staged files in lint-staged, and type-aware Oxlint plus `tsc` 7 in CI. Biome stays a detected alternative, and Vite+ waits until 1.0.

## Three tools pull ahead while ESLint gains 1.3x

Oxlint has been 1.x stable since June 2025 and ships roughly weekly. **v1.89.0 landed on 19 October 2026** ([oxc releases](https://github.com/oxc-project/oxc/releases)). The docs list **871 rules, 334 with auto-fixes**. Ported plugin sets include ESLint core, typescript-eslint, unicorn, react, react-hooks, import, jsx-a11y, jest, vitest, jsdoc, nextjs, node, promise and vue ([oxc rules](https://oxc.rs/docs/guide/usage/linter/rules.html)). Older comparison posts claiming "~300 rules, no auto-fix" are stale. Type-aware linting went **stable on 22 July 2026 with 59 of 61 typescript-eslint type-aware rules**. Vendor benchmarks show it **12-18x faster than ESLint plus typescript-eslint**, for example on the vscode repo: 83.2 s against 6.96 s ([Oxc type-aware stable](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). ESLint-compatible JS plugins have run in **alpha since March 2026**. Pass rates are 100% for ESLint built-ins and react-hooks and 99.99% for ESLint Stylistic. A real repo that mixes native and JS-plugin rules gets 4.8x rather than 50-100x ([Oxc JS plugins alpha](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha)). The headline "50-100x faster" holds only for native rules ([VoidZero 1.0](https://voidzero.dev/posts/announcing-oxlint-1-stable)).

oxfmt reached **beta on 24 February 2026**. It claims **100% Prettier conformance for JS/TS, more than 30x faster than Prettier and more than 3x faster than Biome**, and has built-in Tailwind, import and package.json sorting. Its blocking gap is **no Prettier plugin support**, which the project calls the condition for 1.0 ([Oxfmt beta](https://oxc.rs/blog/2026-02-24-oxfmt-beta)).

Biome sits at **2.6.2, published 21 October 2026**, with no 3.0 announced ([npm](https://registry.npmjs.org/@biomejs/biome)). v2.6 added Markdown, YAML and SCSS formatting, a `biome migrate stylelint` command and Tailwind v4 class sorting ([Biome v2.6](https://biomejs.dev/blog/biome-v2-6/)). Its weakness is type awareness. Biome runs its own inference engine instead of `tsc` and has only **seven rules in its `types` domain** ([Biome v2.4](https://biomejs.dev/blog/biome-v2-4/)). At launch, `noFloatingPromises` caught about **75% of what typescript-eslint catches** ([Biome v2](https://biomejs.dev/blog/biome-v2/)). It also cannot run ESLint plugins. Custom rules come from GritQL or a JS plugin API that is still a developer preview ([Biome plugins](https://biomejs.dev/linter/plugins/)).

ESLint is at **v10.13 (16 October 2026)**. It uses flat config only, and v9 reached end of life on 6 August 2026 ([ESLint v10](https://eslint.org/blog/2026/02/eslint-v10.0.0-released/)). Its one performance feature is multithreading via `--concurrency`. That flag yields **1.30x typically and 3.01x at best**, and it can slow down when config and plugin startup are heavy ([ESLint multithread](https://eslint.org/blog/2025/08/multithread-linting)). The notes found no Rust rewrite or performance roadmap. The bigger problem is that **typescript-eslint 8.71 refuses TypeScript 7** (peer range `<6.1.0`) and waits on the 7.1 programmatic API ([dev.to TS7 guide](https://dev.to/fabwaseem/typescript-7-upgrade-guide-what-breaks-eslint-nextjs-and-real-benchmarks-3m16)). The official workaround aliases `typescript` to `@typescript/typescript6`. Under that alias ESLint resolves types with TS 6 while `tsc` checks with TS 7, so the two can disagree ([TS 7 announcement](https://devblogs.microsoft.com/typescript/?p=5246)).

| Tool (Oct 2026)    | Status           | Speed claim                                      | Type-aware                        | Formats                  | Ecosystem plugins             |
| ------------------ | ---------------- | ------------------------------------------------ | --------------------------------- | ------------------------ | ----------------------------- |
| Oxlint + tsgolint  | 1.89 / v7 stable | 50-100x native rules, 12-18x type-aware (vendor) | 59/61 ts-eslint rules, needs TS 7 | via oxfmt (beta)         | ESLint JS plugins, alpha      |
| Biome              | 2.6.2 stable     | formatter ~35x Prettier (vendor)                 | 7 rules, own inference            | built in, many languages | GritQL; JS plugins in preview |
| ESLint + ts-eslint | 10.13            | `--concurrency` 1.3-3x                           | full, but TS ≤ 6.0 only           | none (Prettier)          | complete                      |
| Vite+ (`vp check`) | beta, pre-1.0    | bundles Oxlint + oxfmt                           | via tsgolint                      | oxfmt                    | as Oxc                        |

Independent numbers are thin but point the same way. On a 403-file Next.js repo, **Oxlint took 118 ms, Biome 131 ms and ESLint 9 took 9,555 ms** ([DEV benchmark](https://dev.to/fabwaseem/oxlint-vs-biome-vs-eslint-in-2026-benchmarked-on-a-real-nextjs-codebase-3lal)). A hyperfine run on about 190 tsx files measured **`oxlint` at 219 ms, `biome check` at 269 ms and `oxlint --type-aware` at 560 ms** ([peterbe.com](https://www.peterbe.com/plog/benchmarking-oxlint-vs-biome)). Between the two Rust tools the gap is small. The gap to ESLint is roughly two orders of magnitude.

## TypeScript 7 reshapes the typecheck step

TypeScript 7.0 replaced `tsc` with the Go port on **8 July 2026**. Full builds got 8.9-11.9x faster with the default four checkers: vscode dropped from 125.7 s to 10.6 s and sentry from 139.8 s to 15.7 s. In the editor, time to first error in the VS Code repo fell from about 17.5 s to under 1.3 s ([TS 7 announcement](https://devblogs.microsoft.com/typescript/?p=5246)). Small repos gain less, about 5x, because startup dominates. Hono's 189 files went from 3.01 s to 0.58 s ([dev.to TS7 guide](https://dev.to/fabwaseem/typescript-7-upgrade-guide-what-breaks-eslint-nextjs-and-real-benchmarks-3m16)). The cost of upgrading is that many TS 6 deprecations are now hard errors, including `baseUrl`, `moduleResolution node10` and `target es5`. Language-service plugins and Vue, Svelte and Astro template support are missing from the new LSP ([TS 7 announcement](https://devblogs.microsoft.com/typescript/?p=5246)).

TS 7 is also what tsgolint pins to: version v7.0.2000 tracks TypeScript 7.0.2. With `--type-check`, Oxlint reports compiler errors from the same program it builds for type-aware rules ([Oxc type-aware stable](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). That turns two CI steps, type-aware lint and `tsc --noEmit`, into one program build. The same coupling means a repo that cannot move to TS 7 cannot use tsgolint. InfoQ adds that one autofix once removed a required type assertion ([InfoQ](https://infoq.com/news/2026/09/tsgolint-oxlint-typescript)). Type-aware fixes deserve a review rather than blind application in a hook.

Vite+ wraps Oxlint, oxfmt, Vitest, Rolldown and a task runner behind `vp check`. It went **beta on 22 August 2026 and is still pre-1.0** ([InfoQ Vite+](https://infoq.com/news/2026/08/vite-plus-beta)). Its v0.2.6 release bundled Oxlint 1.75 while upstream stands at 1.89 ([release](https://newreleases.io/project/github/voidzero-dev/vite-plus/release/v0.2.6)). For a hub that ships templates to many repos, adopting Vite+ would swap the bundler and test runner just to change the linter. That is too much blast radius for this goal.

## Pocock's published advice predates the fast-tool wave

The research ran over a dozen searches and fetches and **found no Matt Pocock content naming Oxlint, oxfmt, Biome, tsgo or Vite+**. YouTube Shorts and X were largely unreachable: the X fetch returned HTTP 402 and the Shorts page returned only page chrome. A short could therefore exist without being indexed. What he has published is consistent. His AIHero article, updated 16 January 2026, treats the `tsc` typecheck as cheap feedback and Husky as the enforcer before every commit. It runs **lint-staged with Prettier** and says "we could also run ESLint here" ([AIHero](https://www.aihero.dev/essential-ai-coding-feedback-loops-for-type-script-projects)). His 2026 talk, known only through secondary summaries, frames lint, tests and typecheck as the cheap automated layer before sub-agent review and human review ([daily.dev summary](https://daily.dev/posts/fixing-the-pr-bottleneck-matt-pocock-aihero-jyn4aj6sm)). The closest match in substance comes from Philipp Spiess, not Pocock. He moved lint, typecheck and tests from CI into a pre-commit hook for agents, using oxfmt, oxlint, bun test and tsgo ([X](https://x.com/PhilippSpiess/status/2014301641239847404)). If the reader remembers a specific Pocock short, its tool choice and numbers belong in this report only after someone confirms the link.

## Feedback reaches the agent only on exit 2

Claude Code hooks have a property that decides token cost. For PostToolUse, **"Claude never sees stderr from a hook that exits 0."** Exit 2 sends stderr back as feedback. JSON `decision: "block"` with a `reason`, or `additionalContext`, does the same ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). Oxc's official recipe runs `oxlint --fix` then `oxfmt` on `tool_input.file_path`, and it exits 0 whenever the tools run ([Oxc coding agents](https://oxc.rs/docs/guide/usage/coding-agents.html)). As written, that recipe silently fixes what it can and **hides every remaining error from the agent**. The errors surface later at commit, when they cost a full extra turn. The cheaper design, inferred from the docs and untested here, follows three rules. Auto-fix and format first. Then re-lint without fixing and, only if diagnostics remain, print them tersely to stderr and exit 2. Stay silent on success so a clean edit adds zero tokens. Biome's v2.5 notes recommend its `concise` reporter for coding agents ([Biome v2.5](https://biomejs.dev/blog/biome-v2-5/)). Oxc's agent docs use `--format=agent` but do not document it ([Oxc coding agents](https://oxc.rs/docs/guide/usage/coding-agents.html)), so check its output before relying on it. No source measured hook latency or token savings, and no source measured single-file startup for any of these linters. Those are the numbers to take locally before a hub-wide rollout.

| Step                                | Recommended tool and invocation                                                                                             | Why                                                           | Keep out                                                          |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------- |
| (a) PostToolUse hook, `Edit\|Write` | `oxlint --fix` + `oxfmt` on the one file, then `oxlint` again → exit 2 with remaining diagnostics                           | sub-second, auto-fix removes most findings, silent on success | type-aware rules, `tsc`, tests (whole-program cost on every edit) |
| (b) lint-staged on commit           | `oxfmt` + `oxlint --fix` on staged files                                                                                    | fits skilly's < 3 s pre-commit budget                         | `--type-aware` by default; opt-in for small repos only            |
| (c) CI lint step                    | `oxlint --type-aware --type-check` + `oxfmt --check`, or `tsc` 7 if not merged                                              | one TS 7 program covers type-aware lint and compiler errors   | ESLint, except via `eslint-plugin-oxlint` for rules Oxc lacks     |
| (d) IDE                             | Oxc extension (VS Code/Cursor/Zed/JetBrains, `oxlint --lsp`), `source.fixAll.oxc` on save, `oxc.typeAware`; TS 7 native LSP | same binary and config as hook and CI                         | ESLint extension once migrated                                    |

The per-step split follows the cost of building a TS program. The edit hook and lint-staged see one file or a handful, so they get only syntactic rules, which run in milliseconds. Type-aware rules need the whole program, and even tsgolint's best case on a mid-size repo is about 0.75-1 s; vscode-scale repos take about 7 s ([Oxc type-aware stable](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)). They belong at push or CI, where skilly's `verify.json` already runs `typecheck` at push and `lint` at CI. The Oxc editor integration runs the same `oxlint --lsp` from the local install and supports fix-on-save across VS Code, Cursor, Zed, JetBrains and Neovim ([Oxc editors](https://oxc.rs/docs/guide/usage/linter/editors.html)). One config file then drives all four steps. Biome offers the same single-config property, with `--staged` for commits, `--changed` for CI and an Open VSX extension for Cursor ([Biome CLI](https://biomejs.dev/reference/cli/), [Biome VS Code](https://biomejs.dev/reference/vscode/)). Its seven-rule type domain is what loses it the CI step.

Migration is mechanical on both sides. `npx @oxlint/migrate --type-aware` converts ESLint v9/v10 flat config, and `eslint-plugin-oxlint` lets ESLint keep only the leftover rules when a repo needs a hybrid ([Oxc migration](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html)). `oxfmt --migrate` reads Prettier and Biome configs ([Oxfmt beta](https://oxc.rs/blog/2026-02-24-oxfmt-beta)). The hard exclusions are concrete. Repos that depend on Prettier plugins stay on Prettier. Repos with custom Vue, Svelte or Angular parser rules, or custom type-aware JS rules, keep ESLint for those rules ([Oxc JS plugins docs](https://oxc.rs/docs/guide/usage/linter/js-plugins)). Repos pinned below TS 7 can use Oxlint and oxfmt but not tsgolint.

## Conclusion

The decisive change in 2026 is not raw speed, since the Rust linters were already fast in 2025. It is that **TypeScript 7 shipped without an API**, and typescript-eslint is pinned to TS 6 while it waits. Oxc's bet on binding to typescript-go turned that gap into the only fast, fully type-aware path. Every repo that moves to TS 7 is pushed toward Oxlint plus tsgolint whether or not it cares about speed. Biome, betting on its own inference engine, is on the other side of that line for type-aware checks.

For skilly, the templates are already tool-agnostic (`npm run lint`, `npx lint-staged`), so the change lives in what `setup-pre-commit` installs and in the hook recipe, not in `verify.json`. Ship Oxlint and oxfmt as the default. Keep the existing Biome detection in `lib/formatter-ignores.js` for repos that already use Biome. Fix the exit-0 gap in any edit hook skilly distributes, because a fast linter whose findings the agent never sees saves no tokens. Two unknowns justify one local measurement before rollout: single-file hook latency, including `npx` resolution, and whether `oxlint --type-aware --type-check` can fully replace a separate `tsc` step in CI.
