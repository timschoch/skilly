# Config-sync patterns: shared agent config into many repos

Research for [#5](https://github.com/timschoch/skilly/issues/5). Feeds the design call in [#2](https://github.com/timschoch/skilly/issues/2), "config-sync mechanism for `.claude`/`CLAUDE.md`/`AGENTS.md` with project-specific edits".

Question: how to push hub-owned agent config into ~14 consumer repos from CI so per-repo edits survive, and so the PR diff shows at a glance that the shared part moved and the custom part did not.

Constraints: solo user, GitHub Free, no cloud agents. CI opens the sync PRs. A human or a local agent resolves conflicts. Transport already exists, `peter-evans/create-pull-request` in `laica-launcher/.github/workflows/skills-sync.yml`.

---

## 1. What the file formats already give us

These facts from the Claude Code memory docs shrink the problem before any tool choice.

| Fact | Consequence |
|---|---|
| "Block-level HTML comments (`<!-- maintainer notes -->`) in CLAUDE.md files are stripped before the content is injected into Claude's context." | Sentinel markers cost zero context tokens in CLAUDE.md. The usual objection to managed blocks does not apply. |
| "CLAUDE.md files can import additional files using `@path/to/import` syntax… Both relative and absolute paths are allowed… maximum depth of four hops." | Base file plus overlay via import is documented and supported. |
| "Import parsing skips Markdown code spans and fenced code blocks." | An `@path` inside a fence stays inert. Safe to document paths. A marker block must never sit inside a fence. |
| "An import in a project-level memory file is external when its path resolves outside your working directory… shows an approval dialog… If you decline, the imports stay disabled." | Imported shared content must live inside the repo. No `@~/.claude/...` for repo config. |
| "Claude Code reads `CLAUDE.md`, not `AGENTS.md`… create a `CLAUDE.md` that imports it… A symlink also works: `ln -s AGENTS.md CLAUDE.md`." | The AGENTS.md to CLAUDE.md bridge is official. `laica-launcher` already uses the symlink form. |
| `.claude/rules/*.md`: "All `.md` files are discovered recursively… Rules without `paths` frontmatter are loaded at launch with the same priority as `.claude/CLAUDE.md`." | Whole-file granularity for free. A hub-owned rules file needs no import line and no marker. Dropping the file in is the whole install. |
| `.claude/rules/` "supports symlinks, so you can maintain a shared set of rules and link them into multiple projects." | Documented, but useless here. A symlink pointing outside the repo does not survive a CI checkout of a consumer repo. |
| "Splitting into `@path` imports helps organization but doesn't reduce context, since imported files load at launch." | Imports buy structure, not token budget. Do not split for savings. |
| AGENTS.md defines no import or include mechanism. Composition is positional: "Agents automatically read the nearest file in the directory tree, so the closest one takes precedence." | Anything non-Claude agents must see has to be inlined in `AGENTS.md`. That is the only place a merge is unavoidable. |

Local precedent: `~/.claude/CLAUDE.md` already carries a tool-managed region, `<!-- lean-ctx -->` / `<!-- lean-ctx-claude-v3 -->` … `<!-- /lean-ctx -->`, with a versioned inner sentinel. The pattern is in daily use and already understood.

Current fleet: 31 `AGENTS.md`/`CLAUDE.md` files across `~/repo`, 40 to 185 lines each, content almost entirely repo-specific. There is no large shared payload to inline today.

## 2. Prior art

### Sentinel-marker managed regions

| Tool | Markers | Semantics worth stealing |
|---|---|---|
| Ansible `blockinfile` | `# {mark} ANSIBLE MANAGED BLOCK` (`marker_begin=BEGIN`, `marker_end=END`) | "Using a custom marker without the `{mark}` variable may result in the block being repeatedly inserted on subsequent playbook runs." "Multi-line markers are not supported and will result in the block being repeatedly inserted." "When more than one block should be handled in one file you must change the `marker` per task." Markers must be single-line and unique per block. |
| all-contributors | `<!-- ALL-CONTRIBUTORS-LIST:START - Do not remove or modify this section -->` … `<!-- ALL-CONTRIBUTORS-LIST:END -->` | The bot rewrites only between markers. The rest of the README stays untouched. Proven at scale. |
| doctoc | `<!-- START doctoc generated TOC please keep comment here to allow auto update -->` … `<!-- END doctoc generated TOC ... -->` | The block can move anywhere in the file. The markers define ownership, not the position. |
| ruler | `# START Ruler Generated Files` … `# END Ruler Generated Files`, in `.gitignore` only | Worth noting: ruler uses a managed block for `.gitignore` but overwrites `CLAUDE.md`/`AGENTS.md` wholesale. |
| projen | `~~ Generated by projen` | Generated files carry the marker and are read-only. Customization goes back to `.projenrc`, never into the artifact. |

All five share one shape. One contiguous region, single-line comment sentinels, generator owns the inside, human owns the outside, and no merge algorithm anywhere.

### Template with slots, base file plus overlay

- `@file` imports in Claude Code, see section 1. Hub owns the base file, repo owns the overlay, one import line joins them. Depth limit four.
- `.claude/rules/*.md`, the strongest form. No join at all, because the unit of ownership is the file.
- AGENTS.md nesting, nearest file wins, no import. A package-level `AGENTS.md` overrides the root one. That helps monorepos, not a hub-to-consumer split.

### Three-way and template-update tools

- Copier, `copier update`: regenerates a fresh project from the old template version, "compares both version to get the diff from 'fresh project' to 'current project'", applies the template changes, re-applies the diff. Needs `.copier-answers.yml`, a git-tagged template, and a clean git worktree. `--conflict=inline` (default) "updates the file with conflict markers… quite similar to the conflict markers created when a `git merge`"; `--conflict=rej` writes `.rej` files. Runs unattended with `--defaults`.
- Cruft, `cruft update` for Cookiecutter: `.cruft.json` pins the template commit, the variables, and a `skip` list. `cruft check` exits 1 when the template moved, which suits CI. The documented automation opens two PRs, one accepting the template changes and one rejecting them by bumping `.cruft.json` alone.
- Yeoman conflicter: "every write happening on a pre-existing file will go through a conflict resolution process. This process requires that the user validate every file write that overwrites content." Interactive by design, so unusable unattended.

### CI transport

- `BetaHuhn/repo-file-sync-action`: "By default if a file already exists in the target repository, it will be replaced", with `replace: false` to opt out per entry. Nunjucks templating, `deleteOrphaned` for directory syncs, one PR per target repo. Whole files only, no block or partial sync.
- `peter-evans/create-pull-request`: already the PR mechanism in the nightly workflow. Nothing to change.

### Git-native options, ruled out

`.gitattributes` `merge=ours` cannot ship with the repo. "The definition of a merge driver is done in the `.git/config` file, not in the `gitattributes` file." The gitattributes built-ins are `text`, `binary`, and `union`, with no `ours` driver. Every consumer repo would need a manual `git config merge.ours.driver true`, and a CI checkout has none of it. A submodule or subtree for a shared config directory works, but it adds a second thing to update per repo for a payload of a few kilobytes.

## 3. Candidate mechanisms

### A. File-level ownership, no merge

Hub owns whole files, repo owns whole files, and the two sets never intersect. Shared content lands in `.claude/rules/skilly-*.md`, which loads automatically with no import line, and in `.agents/skills/**`, which the hub already owns under the existing "never hand-edit a consumed copy" rule. CI overwrites hub files wholesale and never touches `AGENTS.md`/`CLAUDE.md` after bootstrap.

- No conflicts are possible. Review reduces to "did a hub file change?", because the whole diff is shared content by construction.
- Transport is off the shelf, either `repo-file-sync-action` or a `cp` step plus `create-pull-request`. No custom editor to write or debug.
- Matches the existing skills contract. Nothing new to learn.
- Against: `.claude/rules/` is Claude Code only. Codex and other AGENTS.md readers see none of it.
- Against: a per-repo exception to a shared rule has nowhere to live except a repo-owned file that contradicts the hub file. Claude Code concatenates rather than overrides, and "if two rules contradict each other, Claude may pick one arbitrarily."

### B. One managed block in `AGENTS.md`

`AGENTS.md` stays repo-owned except for one contiguous sentinel-delimited region that CI replaces byte for byte. `CLAUDE.md` stays a symlink to `AGENTS.md`, the `laica-launcher` pattern, or becomes a `@AGENTS.md` one-liner where Claude-specific extras are wanted.

```
<!-- skilly:begin v3 -->
…hub-owned text…
<!-- skilly:end -->
```

- Works for every agent regardless of import support, because the shared text sits physically in the file they read.
- The PR diff is exactly the block. Nothing outside the sentinels can change, a diff touching a line outside them is a bug, and the same workflow can check that invariant mechanically.
- Markers are free in CLAUDE.md, since Claude Code strips them before injection, and cost a handful of tokens elsewhere.
- The version sentinel makes drift greppable across the fleet and lets CI skip a no-op.
- Against: needs a small idempotent writer, roughly 30 lines, plus its failure modes. Markers absent, duplicated, reordered, or sitting inside a fenced block. Ansible's own docs show every one of these is a real bug class.
- Against: bootstrapping 14 repos means inserting the empty block once per repo.

### C. Template plus three-way update, Copier or cruft style

Pin a template version per repo in `.copier-answers.yml` or `.cruft.json`. On update, regenerate old and new, apply the diff, and emit conflict markers where both sides moved.

- Handles drift anywhere in the file, not just inside a region. Survives a repo rewriting the shared text.
- `cruft check` gives a real drift signal, and the two-PR pattern, accept or reject by bumping the pin, is a proven unattended workflow.
- Against: heavy for the payload. An extra state file per repo, a clean-worktree requirement, and a git-tagged template.
- Against: conflict markers land in the PR, which stays red until a human or local agent resolves it. That is the opposite of trivially reviewable.
- Against: two new tools in a loop that already works with `skills update` plus a PR.

## 4. Recommendation: A, with a minimal B for the AGENTS.md join

For one user, 14 repos, and a few kilobytes of shared text:

1. Everything longer than a few lines becomes a whole hub-owned file. `.claude/rules/skilly-<topic>.md` for Claude Code rules, `.agents/skills/**` for skills. CI overwrites them and consumers never edit them. That covers most of the payload with a mechanism that cannot conflict and needs no custom code.
2. `AGENTS.md` carries exactly one managed block, kept small by policy. The handful of universal rules plus pointers into the hub-owned files. Sentinels `<!-- skilly:begin vN -->` and `<!-- skilly:end -->`, single-line, unique, never inside a fence, version in the opening marker. This is the only file where per-repo and shared text coexist, and the only place that needs a writer.
3. `CLAUDE.md` stays a symlink to `AGENTS.md` where there is no Claude-specific content, per the official guidance and existing `laica-launcher` practice. Where there is, a `@AGENTS.md` import plus the extras below it.
4. CI guards, CI does not merge. If markers are missing, duplicated, or the diff touches a line outside the block, fail the job and say so. Never append, never guess. Deleting the block is a valid opt-out.
5. No Copier, no cruft, no git merge drivers, no ruler. Ruler's own answer to this problem is overwriting `CLAUDE.md` wholesale, which would destroy the per-repo content that is the entire point here.

The reason for that ordering: the merge problem exists only for AGENTS.md, because AGENTS.md is the one format with no composition mechanism. Every other artifact can be owned whole, and a whole-owned artifact cannot conflict. Solve the small remainder with a managed block, and do not buy a merge engine for the part that never needed one.

## 5. Open questions for #2

- Does the shared content need to reach non-Claude agents at all today? If Claude Code is the only reader, drop step 2 and the mechanism becomes pure whole-file sync.
- Per-repo exception to a hub rule: contradict it in a repo-owned file, or add an opt-out list to the hub config? Claude Code resolves contradictions arbitrarily, so contradiction is not a design.
- Marker vocabulary: `skilly:begin` versus the house style already in `~/.claude/CLAUDE.md`, `<!-- skilly -->` … `<!-- /skilly -->`. Consistency argues for the house style.
- Bootstrap: hand-insert the empty block in 14 repos, or let the first sync append it when absent? Appending contradicts the "never guess" guard.
