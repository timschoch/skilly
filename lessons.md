# Lessons

- When the user has placed a file at a deliberate location, ask before moving it — even to a previously agreed path. State the intended move and wait for OK.
- The user (and other agents) edit this repo concurrently. A surprise rename or new dir is likely intentional, not an error. Never "fix" it — report the mismatch and ask before renaming or reverting anything I did not create.
- Pushed + closed a wayfinder ticket without showing the work → rule added to CLAUDE.md (Sign-off): stage finished work and stop; commit/push/PR only after the user signs off.
- "Workspace rules" means `bundles/workflow/rules/` (the always-on rules the workflow bundle syncs to consumers) — not `~/.claude/rules/`. Never write to `~/.claude` for a fleet-wide rule; it belongs in the hub.
- A surprising bundle layout may encode an intended agentic flow, not a bug. Declared it a "clear bug" and merged a fix (#25) — the real design: onboard installs only the entry skill, the skill decides the rest. Before "fixing" bundle contents, state the surprise and ask for the intent.
- Offered the git-shortcuts Slack summary after a merge in this repo → rule added to CLAUDE.md (No Slack): skilly never gets Slack posts; skip that step without asking.
- Recommended symlinks and hand-copied rules over `skilly setup`/`add` for the hub's own setup, calling the real path unsafe on four counts — all four were the mechanics working (dead pins get repaired, unclaimed skills get dropped, Sync PRs never touch `bundles/`). Before declaring a hub verb unsafe, run it against evidence (`npx skills@1.5.23 add timschoch/skilly -l`, the CLI source), and prefer the real path: dogfooding is what found the dead pins and the `GIT_*` hook leak.
- Bundled `use-twenty-mcp` from `twenty-codex-plugin` for Claude Code consumers and split a bundle around it; the user spotted the codex vs claude package paths. The skill names Codex as the agent and its setup configures Codex MCP. When a vendor ships skills per harness, grep each `SKILL.md` for the harness name (`grep -i codex`) before bundling; prefer the Claude-targeted skill and drop harness-specific duplicates.
- Put benchmark scores, prices, version comparisons and "why we chose it" into a consumer rule (`workflow-model-selection.md`); the user called it slop. A consumer rule states current practice in plain sentences: no clever labels ("Match ceremony to the task"), no jargon ("cap a cost tail"), no reasoning the reader does not act on. The reasoning stays in chat or an ADR.
- Hardcoded `model:` and `effort:` in skills (`plan-critics` critics, `audit-agent-history`); the user called it a list that drifts. A skill names the kind of work ("deep reasoning over many logs"), never the model or the effort. The agent that starts the subagent picks them. Exceptions: code that cannot read a rule (`lib/setup.js`) and tests that need fixed models (`term-check/probe.sh`).
- Handed over UI changes to the setup-interview prototype after server smoke tests and screenshots of injected states; the user asked "do you test before I test?" Before handing over UI work, run it end to end: real server, a real browser clicking the real buttons, a fake agent answering (`npm run e2e` in `interview-channel/`). Screenshots of injected states prove the look, not the flow.
- Posted a plan with open decision 10; the user replied "you can --cp when you're done" and then asked a question about 10. I read the first line as "go" and started to code. Permission for a later step (commit, push) is not a go. An open decision or a question from the user means: answer, then wait for an explicit "go".
- Told "apply the changes and bring it to prod, then colin picks it up", I edited colin, pushed a branch and opened a colin PR. "Bring it to prod" means the skilly hub; each consumer repo's own agent makes its changes. From a skilly session, never edit, push or open a PR in a consumer repo — ship the hub change, then hand the consumer agent the text.
- Wrote a `setup-project` step as a paragraph with an inline JSON hook, a `.gitignore` fix and config questions, plus chat residue ("not a setup skill"); the user rejected it. A `setup-project` step is one line: the question and the commands. Wiring a feature needs (hooks, settings) goes in a script beside the skill (`scripts/setup.mjs`) or in a setup skill. Repo-wide conventions (`.temp/` gitignored) belong to repo init, never to a feature skill.
- Added `\.gen\.` to the shared `generated` naming allow for one TanStack file, and picked my own recommendation on a decision the user had not answered. A generated-file exception goes in the bundle's stack file (`naming/references/stacks/<bundle>.json`) with the exact path, never a broad pattern in `naming.json`. An unanswered decision stays open: ask again, never apply the **recommended** pick silently.
